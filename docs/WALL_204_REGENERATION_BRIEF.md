## 最优先：27 道 PLAIN 墙题（惯例错位类）

gold 无任何复杂结构，却没有任何家族命中——失败原因不是 SQL 复杂度，
而是**答案惯例错位**：题面问 "how many / no. of"，gold 却返回**明细列表**
（例：问"多少考生"，gold 是 `SELECT 考生数列` 而非 `COUNT`）；或反之。
这 27 题（`53,92,164,205,207,223,328,338,340,341,343,344,357,359,408,437,441,447,500,581,584,811,812,871,989,1010,1366`）
对定向再生最友好：多生成"COUNT 与明细两种形态"即可显著提高命中率。
注意合规：把该惯例写进 Prompt 属 Dev 反馈规则，须按规范 §2.2 记录，
且不得逐题定制。

## 其余 177 题的再生建议

按分布，重生成 prompt 需覆盖：聚合口径变体（COUNT(*)/COUNT(col)/
COUNT(DISTINCT)、SUM vs COUNT）、复合列选择（题面短语到多列的映射）、
子查询形态（"most X 的 Y" 型）、CASE 比率、日期函数。网关侧可用
`configs/public_v19_*` 风格配置跑 12 采样，产物并入融合池后重跑
`birdfusion fusion`（DE12_POOL 的角色即由此补齐——当前本机无该产物，
`docs/AUDIT_RECHECK_20261106.md` F3）。

## 已排除的离线路径（不要重复尝试）

确定性模板合成（EGS 原型，值集接地）已完整测量：1,194 条合成 SQL 仅 18
题正确、墙题救回 0、对可达错题的正确佐证 3 vs 错误佐证 70——净效应为零。
原因是构造性的：墙题的 gold 恰恰是**不规则结构**（子查询/CASE/复合投影），
模板枚举覆盖不了这种不规则性。原型与测量记录见 §4.2 与
`research/egs_synth_prototype.py`。
